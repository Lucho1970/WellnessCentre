# Repository instructions

Read and follow the repository workflow and all 38 controls below before modifying this solution. Record unmet controls explicitly; a successful build is not privacy, security or hosted acceptance.

For baseline findings and remediation priorities, see [the 29 October 2026 audit](documentation/COMPLIANCE_AUDIT_2026-10-29.md). Reassess findings against the revision being changed; do not treat historical findings as current verification.

For the follow-up on frontend lint tooling and build dependency advisories (F-02/F-03), see [frontend quality gates](documentation/FRONTEND_QUALITY_GATES.md). Its validation does not close the other privacy, security or hosted acceptance findings.

Before preparing tester access or delivery, follow [pilot safety controls](documentation/PILOT_SAFETY_CONTROLS.md). Pilot configuration is private, opt-in and restrictive; do not infer that the existing database contains synthetic records or that a pilot approval grants a role.

## Repository workflow

- Keep `main` clean. Before changing source, tests, configuration, or documentation, switch to a dedicated branch.
- Use `feature/<short-description>` for additions and planned development; use `bugs/<short-description>` for fixes. These user-requested prefixes override the generic `codex/` default.
- Each new task should have its own branch. Check existing branches and working-tree changes before switching; preserve unfinished work and never reset or discard it to start a task.
- Commit meaningful completed changes with the relevant validation evidence. Do not let completed tasks accumulate as uncommitted edits on `main`.
- Run checks appropriate to the change. A broad checkpoint requires frontend build, browser regression, and applicable PHP checks; distinguish local checks from hosted database acceptance.
- Push completed branches to `origin`. Merge reviewed, validated work into `main` according to the user's authorized scope. For a task that only asks for implementation, do not infer authorization to merge it; present the branch for review.
- After an authorized merge, update local `main` and remove the completed local and remote branch when it is no longer needed. Verify it is merged and not used by another worktree; do not force-delete unmerged branches.
- Keep private `.env` files, database dumps, local attachments, dependencies, build output and generated release ZIPs out of new commits. Existing tracked release records are historical; do not delete their files merely to clean Git status.
- Deployment packages do not replace Git commits. Keep deployment instructions, source migrations, tests and maintained documentation versioned. Record the source revision in release manifests when generating packages.

## Ontario health application, security, development and release standard

Version 1.0 — 29 October 2026. Applies to the PHP API, database, React clinic/client/application administration portals, Wellnexa public website, workers, integrations, tests, infrastructure and release packages. MUST, MUST NOT and REQUIRED are mandatory repository policy; SHOULD requires a recorded reason for deviation. These requirements are mandatory instructions for developers and coding agents working anywhere in this repository.

This standard adapts the supplied development/release rules to this solution's actual stack. It establishes review and release gates; it does not implement missing controls, certify compliance or authorize production deployment. Legal duties, regulator guidance and stronger project safeguards are distinguished below. The accountable custodian and qualified privacy/legal reviewer MUST resolve applicability before real personal health information (PHI) is accepted. Clinical, security and operational approval MUST be evidenced rather than inferred from test results.

### 1. Accountability and regulatory scope — GOV

- **GOV-01:** Identify each health information custodian, platform operator, agent, electronic service provider, privacy contact and incident lead. Record custody/control, purposes, clinic boundaries, professions, supported populations, subprocessors and contractual responsibilities. A multi-clinic platform MUST NOT assume that one clinic's authority extends to another's records. Assess HINP classification when services primarily enable disclosure between custodians; serving multiple clinics alone does not decide it. See [PHIPA](https://www.ontario.ca/laws/statute/04p03), ss. 3, 10, 15–17, and [Regulation 329/04](https://www.ontario.ca/laws/regulation/040329), s. 6.
- **GOV-02:** Maintain a dated applicability register: rule, current source/version and commencement status, affected feature/data, accountable reviewer, decision and review date. Cover PHIPA and its regulation; treatment consent under the [Health Care Consent Act](https://www.ontario.ca/laws/statute/96h02); applicable professional college record, consent, advertising and practice standards; accessibility; CASL; and federal privacy/device rules where applicable. Recheck at release and on material changes. Unproclaimed amendments MUST NOT be described as already binding. In particular, independently confirm PHIPA s. 10.1 commencement; electronic access auditing remains mandatory project policy regardless.
- **GOV-03:** Record PIPEDA applicability for commercial non-health data, interprovincial/international flows and other applicable contexts. Ontario's substantially similar PHIPA exemption is not a blanket exemption for every platform activity. See the [federal privacy commissioner's provincial-law guidance](https://www.priv.gc.ca/en/privacy-topics/privacy-laws-in-canada/the-personal-information-protection-and-electronic-documents-act-pipeda/r_o_p/prov-pipeda/).
- **GOV-04:** Document intended use. Registration, scheduling and record access ordinarily fall within Health Canada's administrative/record exclusions; adding diagnosis, triage, clinical prediction, treatment recommendations or device control MUST trigger a function-specific regulatory/clinical assessment before release. Do not assume that calling an app “wellness” exempts it. See [Health Canada's software classification guidance](https://www.canada.ca/en/health-canada/services/drugs-health-products/medical-devices/application-information/guidance-documents/software-medical-device-guidance-document.html), especially 2.1–2.2.
- **GOV-05:** Maintain a data inventory, flow diagram, privacy impact assessment and threat/risk assessment with owners, mitigation and residual-risk decisions. These are project release evidence, not a claim that identical assessment formats are universally prescribed by law. Booking, receipt, attendance and home-address data can be PHI without clinical notes. Use synthetic records in development, screenshots, fixtures, agent prompts and test deployments. Real-data exceptions require explicit custodian/privacy/security authorization and controlled handling.

### 2. Information practices, consent and patient rights — PRIV

- **PRIV-01:** Publish the actual custodian's information practices and accountable contact, including collection/use/disclosure purposes, access/correction and complaint routes. Ensure clinic-specific identity and contact details are accurate in both supported languages. A platform footer or vendor privacy link is insufficient. Map to PHIPA ss. 15–16 and [IPC privacy-program guidance](https://www.ipc.on.ca/en/media/5415/download?attachment=).
- **PRIV-02:** Collect, use and disclose only authorized, necessary information. Document legal authority by purpose and recipient. Distinguish PHI authority, treatment consent, optional notifications and marketing. Do not assume every permitted use needs a checkbox, that every form acknowledgement is valid consent, or that treatment consent authorizes marketing. Where consent is required, preserve purpose, wording/version, time, actor and authority; provide refusal/withdrawal and enforce current restrictions prospectively. See [IPC consent guidance](https://www.ipc.on.ca/en/health-individuals/consent-and-your-personal-health-information).
- **PRIV-03:** Enforce restrictions at server read, search, list, preview, write, export, assignment and worker dispatch boundaries. Recheck current membership, permission, recipient and restriction after queue delay and immediately before sensitive effects; control concurrent revocation. No automatic administrator/emergency bypass. Any statutory exception or emergency access requires an approved legal basis, narrowly scoped implementation, reason, audit and subsequent review.
- **PRIV-04:** Verify capacity and representative authority for each purpose. A parent, shared email address, booking payer or caregiver MUST NOT automatically gain account access or treatment authority. Implement supported minors/dependants/substitute decision-maker flows with separate identities, scope, expiry and revocation; otherwise document a safe assisted process and explicit product limitation. Treatment consent is a practitioner responsibility and cannot be reduced to registration acceptance. [HCCA](https://www.ontario.ca/laws/statute/96h02), ss. 4, 10–11, 20; [IPC consent guidance](https://www.ipc.on.ca/en/health-individuals/consent-and-your-personal-health-information).
- **PRIV-05:** Provide a tested access/correction process, automated or controlled manual: intake, identity/authority verification, custody review, due-date tracking, lawful extension/refusal, severance, fees where permitted, protected delivery, receipt and complaint information. Track the normal 30-day response period and any lawful extension separately. Preserve original records, author/time/reason and corrections or statements of disagreement. Portal access to selected forms/receipts alone does not fulfill every request. See PHIPA ss. 52–55, [IPC patient-inquiry guidance](https://www.ipc.on.ca/en/media/5415/download?attachment=) and [IPC correction guidance](https://www.ipc.on.ca/en/health-organizations/access-and-correction/correction).
- **PRIV-06:** Approve a record-class/profession-specific retention schedule covering clinical records, consent, receipts, messages, audit, backups and provider logs, including minor-age triggers, legal holds, closure/succession, secure transfer and disposal evidence. Do not assign one universal period or destroy records automatically on account closure/consent withdrawal. For example, [CMTO's record standard](https://www.cmto.com/rules/standard-of-practice-record-keeping/) uses ten years after the last visit, or ten years after turning eighteen for patients under eighteen at the visit; verify the applicable profession and facts before configuring retention. Test hold enforcement and backup expiry/restoration without resurrecting disposed data into active use.
- **PRIV-07:** Maintain and rehearse a breach runbook: immediate internal escalation, containment, evidence preservation, impact assessment, recovery and corrective action. Notify individuals at the first reasonable opportunity where PHIPA requires it, including the right to complain to IPC; assess the prescribed IPC reporting circumstances separately and notify IPC at the first reasonable opportunity where required. Assess professional-college notices, including applicable 30-day triggers, and annual IPC breach statistics due March 1 for the preceding year. Do not substitute a generic 72-hour rule. Sources: [IPC reporting](https://www.ipc.on.ca/en/health-organizations/report-a-privacy-breach), [IPC response guidance](https://www.ipc.on.ca/sites/default/files/legacy/2018/10/health-privacy-breach-guidelines.pdf), [IPC annual statistics](https://www.ipc.on.ca/en/health-organizations/report-a-privacy-breach/annual-reporting-of-privacy-breach-statistics-to-the-commissioner). Verify each year's deadline and filing instructions.

### 3. Identity, sessions, authorization and tenant separation — AUTH

- **AUTH-01:** Use the existing supported identity clients and backend JWT validation. Verify signature/algorithm, issuer, audience, tenant, expiry, scope and identity realm. Fail closed on invalid/unknown identity or unavailable required authority. Do not implement ad hoc passwords or trust UI visibility, client-provided clinic IDs or unverified token contents.
- **AUTH-02:** Enforce clinic, active membership, explicit privilege, record relationship, consent restriction and minimum fields on every server operation. Public, client, practitioner, reception, clinic administrator and central application administrator are distinct authorities. Central billing/support privileges MUST NOT imply clinical-record access. Include negative cross-clinic/record/role tests and stale principal/revocation tests. Re-evaluate historic care relationships and broad scheduling delegation for ongoing necessity.
- **AUTH-03:** Maintain an approved session design for staff and clients: MFA for privileged/workforce access, idle/absolute limits, reauthentication for sensitive administration, revocation, departure and lost-device procedures, and clearing sensitive UI state. These are project security requirements; verify actual identity-provider configuration. A token's expiry or silent renewal alone is not an idle timeout.
- **AUTH-04:** Do not persist reusable credentials, bearer/session tokens or PHI in localStorage/sessionStorage. Any existing identity-library cache or limited invitation/action-link storage requires an explicit, time-bounded security exception recording XSS exposure, lifetime, account binding, cleanup and compensating controls before real-data release; do not silently grandfather it. Prefer an approved memory/server session design. Cookie designs require Secure, HttpOnly, appropriate SameSite, CSRF/origin protections and tested logout; do not change authentication architecture casually. Storage of harmless UI preferences is permitted.
- **AUTH-05:** Inventory every API permission with exact scope/role, feature/code path, runtime principal, admin-consent requirement and actual deployed grant. Restrict mail application access to approved senders and database runtime access to required objects/operations; use separate migration credentials. Broadening grants, clinic reach, support access or authentication architecture requires explicit human authorization.

### 4. Security engineering and data flows — SEC

- **SEC-01:** Never commit secrets, private environment files, dumps, attachments or production data. Browser configuration and bundles are public. Scan tracked source and final artifacts for credentials/private keys/tokens, including historical exposure when indicated; report paths and redacted classifications, never secret values. Rotate confirmed exposed credentials and assess access. Environment examples MUST contain placeholders only; public identifiers are not automatically secrets.
- **SEC-02:** Require HTTPS and verified TLS for production external transport. Document database transport; use verified TLS for network database connections or assess a demonstrably protected local alternative. Require encryption at rest/backups, key ownership/rotation/recovery, restricted infrastructure access, patching and restore evidence. PHIPA's safeguard duty does not establish one universal cryptographic configuration; these are this project's risk controls. Private PHP/configuration/vendor files MUST remain outside public roots.
- **SEC-03:** Establish and verify per-host HTTPS redirects, HSTS where safe, CSP including frame restrictions, nosniff, referrer policy, exact CORS origins and no-store for PHI responses. Review browser/session cache, service-worker, download and shared-device behavior. Local .htaccess or a landing-page policy is not proof for every deployed portal/API host. Do not disable TLS verification or authorize arbitrary hosts/redirects.
- **SEC-04:** Validate type, format, range, length, enumeration and ownership at the server. Use prepared SQL, allowlisted dynamic identifiers, context-specific output encoding and safe URL schemes. Avoid unsafe HTML sinks, eval/dynamic execution and untrusted remote scripts. Any required HTML rendering needs maintained sanitization, hostile-content tests and human security review. Keep PDF PHP/JavaScript/remote-resource execution disabled. Treat stored data and provider responses as untrusted.
- **SEC-05:** Bound request bodies, uploads, response sizes, pagination, query ranges and worker batches. Apply rate/abuse controls to sign-in helpers, public enquiries, exports and costly integrations. Test denial-of-service, duplicate submission, concurrency, timeouts and uncertain outcomes. Uploads require allowlisted formats, verified content, size limits, private storage, malware controls and authorized retrieval. CSV/export designs must address formula injection and unintended data disclosure.
- **SEC-06:** Audit sensitive reads/searches/downloads, writes, denials, consent/privilege changes and exports with actor/realm, clinic, resource IDs, action/outcome, timestamp and correlation. Exclude clinical bodies, tokens and unnecessary identifying content. Fail closed when a required disclosure/transaction audit cannot persist. Restrict review, monitor anomalies and protect audit integrity through database privileges and independent retention/monitoring. Document direct SQL, operator, worker, provider and web-server logging beyond the API audit boundary.
- **SEC-07:** Handle errors deliberately with safe user messages and redacted correlation diagnostics; never leak SQL, stack traces, authorization headers, full payloads or provider credential URLs. Do not swallow errors silently. Preference/storage fallbacks may be narrow, documented and harmless. Ensure proxies, APM, support tools and provider logs redact sensitive URL/query data as well as bodies.
- **SEC-08:** Maintain an endpoint/subprocessor register: actual hostname, owner, purpose, fields, auth/permission, transport, geography/support access, retention/deletion, onward processing, incident terms, failure/retry behavior and approval evidence. Include identity providers, mail, SMS, address validation/routes/maps and configured relays/webhooks. Geographic location alone does not establish legality; do not invent a general PHIPA Canada-only hosting rule. New external services, telemetry, pixels, remote scripts or third-party PHI transmission require explicit privacy/security authorization. Do not send patient data to AI services without a separately approved use and safeguards.
- **SEC-09:** Keep clinical details in the portal. Minimize external email/SMS/calendar content, verify recipients/preferences, distinguish provider acceptance from delivery and avoid unsafe retries. Apply opt-out/suppression across shared senders and clinics without disclosing other clinics' records. Classify each message for CASL; commercial messages need applicable consent, identification and unsubscribe controls unless a documented exception applies. An appointment purpose does not automatically exempt promotional content. [CRTC guidance](https://crtc.gc.ca/eng/com500/faq500.htm/).

### 5. Development, dependency and quality rules — DEV

- **DEV-01:** Before edits, inspect root/nested instructions, Git changes/branches, affected package and lock files, Composer requirements, TypeScript/build/lint/test configs, deployment scripts, database migrations and maintained documentation. Preserve architecture and compatible Node/npm/PHP/React/TypeScript/database toolchains. Use this repository's feature/bugs branches; preserve unfinished work; commit and push completed work. Do not merge or deploy without authorization.
- **DEV-02:** Treat generated/modified code as untrusted until reviewed. Keep scope focused. Do not weaken strict typing, lint/build/test/security controls, hide failures, skip tests to accommodate defects or claim readiness from compilation alone. Avoid any/as any, ts-ignore, unjustified assertions, unhandled promises and empty catch blocks; document narrow unavoidable cases. Keep modules readable and authorization decisions explicit.
- **DEV-03:** Use exact lockfile restores (`npm ci`, `composer install`) in a clean release environment; do not replace locks with opportunistic updates. Audit full and runtime dependency trees, classify direct/transitive and runtime/build-only paths, deployed inclusion, exploit conditions, licence/maintenance and remediation. Never use forced audit fixes or unreviewed major upgrades. Adding/replacing runtime dependencies or changing supported toolchains requires human authorization. Critical/high runtime vulnerabilities block release pending remediation or authorized, documented security acceptance; build-tool findings require their own exposure decision and remediation plan.
- **DEV-04:** Run the existing content/i18n/strict TypeScript checks and production builds for every affected surface. Lint must actually execute using a declared, configured tool. Run applicable PHP policies/syntax and meaningful regression tests. No test should merely duplicate implementation. Test successful, empty, malformed, unauthorized/cross-clinic, missing, unavailable, throttled, interrupted, duplicate and concurrent outcomes; recheck sensitive state after permission changes.
- **DEV-05:** UI work requires keyboard/focus/dialog restoration, semantic labels/errors, contrast, screen-reader checks, loading/denial recovery, responsive widths, zoom, supported themes and bilingual content. WCAG 2.2 AA is the project target. Record the actual AODA/IASR applicability (organization size/type, public/internal surface, exceptions); do not equate that project target with the statutory baseline. See [Ontario website requirements](https://www.ontario.ca/page/how-make-websites-accessible). Core inaccessible workflows block release; an automated browser pass is not a complete accessibility audit.
- **DEV-06:** Review bundle sizes/dependencies, repeated network calls/renders, indexed and bounded queries, throttling, event/timer/subscription cleanup and representative-volume performance. Investigate warnings with recorded impact; do not silence limits to remove warnings.

### 6. Validation, deployment and release gates — REL

**REL-01 — Evidence ledger:** For every control above record Implemented, Partial, Missing, Unverified or Not applicable; source revision, file/test/operational evidence, owner, dated reviewer decision and next action. “Implemented” means only the verified scope. A not-applicable decision needs reasoning. Missing repository evidence is not proof of organizational noncompliance. Neither an automated audit nor this document can guarantee all security considerations are met.

**REL-02 — Local checkpoint:** For a broad checkpoint, run both frontend builds and browser regressions plus applicable PHP syntax/policy and disposable SQL/HTTP suites. Identify the suites omitted by default Playwright configurations; use the dedicated admin/application/invitation configs when affected. Report exact commands, runtime versions, counts, failures and untested scenarios. Database tests MUST use explicit disposable synthetic databases, never infer permission to use hosted credentials. Fix test-environment problems transparently and retain initial failure context.

Typical commands (run from the indicated directory; inspect current scripts first):

```text
Frontend: npm ci; npm audit --json; npm audit --omit=dev --json
Frontend: npm run lint; npm run build; npm test
Frontend: npx playwright test --config playwright.build.config.ts
Frontend: npx playwright test --config playwright.application-admin.config.ts
Wellnexa: npm ci; npm audit --json; npm run lint; npm run build; npm run test:browser
api: composer install --no-interaction; composer validate --strict; composer audit --format=json
Repository: php -l <each applicable PHP file>; php api/tests/<applicable policy test>.php
Repository: ./scripts/test-recurring-sql.ps1 -MariaDbDirectory <disposable-runtime> -IntegrationTest <suite>
```

Commands separated above describe independent checks; capture every exit code. Their presence here does not assert that every command passed or that production deploys need development dependencies.

**REL-03 — Artifact and hosted acceptance:** Inspect the actual package, including secrets, PHI/test fixtures, HTTP/localhost/development endpoints, source maps, debug output, dependency inclusion, accidental private files and environment configuration. Record package version, exact source SHA, branch/tag, lockfile hashes, runtimes, build ID/date and manifest. Test that artifact in approved non-production hosting with representative non-admin, client, practitioner, clinic and central admin identities; verify real API/database/identity boundaries, migrations, revocation, concurrency, backups, headers, integration failures and rollback. Mocked browsers/local SQL do not establish hosted acceptance.

**REL-04 — Release decision:** Mark NOT READY FOR RELEASE while required checks fail, high-impact access/privacy/security defects remain, required controls/evidence are missing, permissions/endpoints are unapproved, artifact provenance is unknown, or rollback/hosted acceptance is incomplete. No exception may waive a legal duty. Internal-policy exceptions require the accountable privacy/security/clinical owner as applicable, exact scope, compensating controls, expiry and retest. Document approval separately from implementation authorization. Use synthetic data until the real-data gate is signed.

**REL-05 — Human approval and operations:** Obtain explicit authorization before production deployment, material data/schema migrations, destructive actions, broadened permissions, authentication architecture changes, new external data flows, unsafe HTML rendering, runtime dependency additions/replacements or supported toolchain upgrades. Existing explicit task authorization counts; do not ask repeatedly. Complete safe preparatory work and produce a reviewable result first. Record current/previous artifact, configuration/grant changes, migration and tested rollback/data-restoration procedure, release owner, smoke tests, monitoring and incident contact. Require custodian/privacy, security/operations, clinical and release-owner sign-off within their responsibilities. Documentation edits do not authorize deploying or merging.

**REL-06 — Completion report:** Include requested/result summary; every changed file and purpose; exact dependency versions, permission/consent and endpoint/data-flow changes (or explicitly none); security/privacy findings; exact validation commands/results; warnings, omitted checks, assumptions, hosted/operational evidence, risks, owner/action and rollback implications. End with exactly one line:

```text
RELEASE STATUS: READY FOR HUMAN RELEASE REVIEW
```

or

```text
RELEASE STATUS: NOT READY FOR RELEASE
```

### 7. Review checklist and maintenance

- [ ] Applicability, custodian/agent roles, profession, intended use and current legal sources approved (GOV).
- [ ] Notice/contact, authority, restrictions, representatives, patient requests, retention and breach process evidenced (PRIV).
- [ ] Identity, session, least privilege and all clinic/record boundaries verified (AUTH).
- [ ] Secrets, encryption, browser protections, injection, abuse controls, audit and vendor flows reviewed (SEC).
- [ ] Dependencies/toolchains, lint, tests, accessibility and performance reviewed (DEV).
- [ ] Reproducible artifact, hosted synthetic acceptance, rollback, monitoring and accountable signatures recorded (REL).

The release owner MUST maintain this checklist with evidence links and unresolved findings, not just checked boxes. Review this standard at least annually and when a relevant law, college standard, security advisory, vendor, feature, incident or deployment architecture changes. Assign named owners before accepting real PHI. Keep historical audits intact; create dated follow-ups against exact revisions.
