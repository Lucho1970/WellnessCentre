# HTTPS enforcement for Netfirms app hosts — 5 November 2026

## Scope and observed baseline

Branch `bugs/https-enforcement` follows the already-pushed `feature/wellnexa-privacy-statement` source at `7f5405a`. This task changes four versioned root `.htaccess` files (`Wellnexa/public/.htaccess`, `hosting/netfirms/portal/.htaccess`, `hosting/netfirms/portal-landing/.htaccess`, `Frontend/public/.htaccess`), two API child rules (`Wellnexa/public/api/.htaccess`, `api/deploy/netfirms/public/.htaccess`) and a new central Admin child rule (`hosting/netfirms/portal-admin/.htaccess`). The roots map to `/public_html/wellnexa.ca`, `/public_html/wellness-common-portal` (both clinic portal hostnames), `/public_html/wellness-portal` (central Admin) and `/public_html/livinlively.ca`. Three deployment builders and the current-artifact verifier are updated to package/check the dedicated Admin child rule instead of the public-site rule copied by Vite. No PHP, JS, dependencies, schema, private configuration, identity grants or mail/SMS flow changes. The Livin Lively public site already had an HTTPS 302 rule; only a short HSTS trial is staged there.

Before this change, verified-TLS `https://` requests succeeded for `wellnexa.ca`, `wellnexa.copihue.ca`, `livinlively.copihue.ca` and `portal.copihue.ca`, so new certificates are not needed. On 5 November, each of those four hosts also returned HTTP 200 without a redirect. The Wellnexa privacy page and both clinic `/client` shells were likewise accessible over HTTP; an HTTP public clinic API returned JSON. Existing project [privacy acceptance](WELLNEXA_PRIVACY_STATEMENT_2026-11-04.md) found missing HSTS/CSP/nosniff/referrer headers on the Wellnexa website. This is current hosted evidence for these requests only; not a full host/header inventory.

Netfirms [documents enabling SSL and adding `.htaccess` HTTPS redirects](https://www.netfirms.com/help/article/enable-your-free-ssl-certificate). The existing Livin Lively public site uses `RewriteCond %{HTTPS} !=on` successfully on this account. [OWASP transport guidance](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html) recommends HTTPS for all pages and rejecting unencrypted API requests where feasible. The new rules use fixed HTTPS destinations, keeping the two clinic portal hosts separate. They reject HTTP `/api` requests before PHP; redirecting after a POST body has arrived would not undo plaintext disclosure. They preserve HTTPS routes and query strings through the existing rewrites.

## Staged rollout

The first source version uses **302** on non-API pages to test live routing without caching a permanent mistake. No HSTS is enabled in this stage. `mod_rewrite` syntax cannot be exercised locally because Apache is not installed; successful source checks do not replace hosted acceptance. The first hosted Wellnexa root upload confirmed a one-hop HTTP `/privacy?lang=fr` → HTTPS 302 with path/query preserved, and the HTTPS page/browser remained healthy. The bare HTTP `/` intermittently returned a cached older 200; a fresh query returned the 302. Crucially, a fresh HTTP `/api/public/services` request still returned JSON 200. The root API rule therefore did **not** protect the nested API on this host.

The second source version tried a nested API denial rule. After the owner uploaded that one file, HTTPS `/api/public/services` and `/api/public/contact` returned hosting 404 pages while the direct HTTPS `catalogue.php` entry still returned JSON. An HTTP API request redirected to `https://wellnexa.ca/public/services`, dropping `/api`. The owner restored the backed-up nested API `.htaccess`; HTTPS `/api/public/services` again returned JSON 200. This hosted failure is retained as a regression finding. The corrected root rules now match the complete `%{REQUEST_URI}` and redirect using that complete path. The owner uploaded the corrected root; HTTP `/privacy` redirected to the same HTTPS path, and HTTPS `/api/public/services` returned JSON 200, but both HTTP API rewrite and direct PHP entry still returned JSON 200. [Apache documents](https://httpd.apache.org/docs/2.4/rewrite/htaccess.html) that child `.htaccess` rules do not inherit parent rewrite rules by default. After the owner uploaded the child-only denial against the corrected root, HTTP `/api/public/services`, direct `catalogue.php?resource=services`, `/api/public/contact` and `/api/public/discovery/options` all returned 403; their HTTPS versions returned JSON 200. Fresh HTTP `/privacy?lang=fr`, `/contact`, `/join` and a missing asset redirected once to the same HTTPS path/query. This demonstrates the tested Wellnexa host only; authenticated API routes and other hosts remain unverified.

4. The owner backed up and uploaded the shared portal root and API child `.htaccess` files one at a time. But fresh HTTP `/admin/index.html` and `/admin/auth/callback` redirected to `https://livinlively.ca`, dropping `/admin`; bare HTTP `/admin` returned an HTTP-to-HTTP directory-slash 301. The owner confirmed the live Admin child held the public site's `.htaccess`, which the full/legacy builders copied from Admin Vite output. After the owner uploaded the dedicated Admin child rule, fresh HTTP `/admin/`, `/admin/index.html`, `/admin/auth/callback` and an unknown Admin path redirected to the same HTTPS host/path; HTTPS Admin/index/callback returned HTML 200. The exact bare `/admin/` URL may still return Netfirms' cached old redirect until its max-age expires, so fresh query URLs were used to prove the new origin rule. Apache [documents](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html) that rewrite rules ignore real directories without a trailing slash by default, and [warns](https://httpd.apache.org/docs/2.4/mod/mod_dir.html) that disabling the slash can expose directory listings. The owner uploaded the corrected child rule with `Options -Indexes`, `DirectorySlash Off` and `RewriteOptions AllowNoSlash`. Fresh HTTP `/admin` now redirects directly to `https://portal.copihue.ca/admin/`; HTTPS `/admin` canonicalizes to `/admin/`; HTTP `/admin/` and callback redirect to the correct HTTPS host. HTTPS Admin/index/callback remained HTML 200, an actual Admin JS asset remained 200, and HTTPS `/admin/assets/` returned 403 rather than a directory listing. The original Admin child backup remains available for rollback.
6. The owner backed up and uploaded the central API child `.htaccess`. HTTP `/api/v1/application/clinics` and direct `/api/index.php` returned 403; HTTPS `/api/v1/application/clinics` retained JSON 401 without a session, and direct HTTPS `/api/index.php` retained JSON 404. No identity provider redirects or grants changed.
7. The owner uploaded the **300-second, host-only HSTS trial** one root file at a time on `wellnexa.ca`, both clinic hosts, `portal.copihue.ca` and `livinlively.ca`. Fresh HTTPS page and nested API responses on all five hosts carried exactly `Strict-Transport-Security: max-age=300`; tested HTTP page redirects and API denials carried no HSTS. The `mod_headers` expression works here and is inherited by child API/Admin directories. After the public Livin Lively root upload, HTTP `/api/v1/site-config` was still JSON 200 because its API child rule had not yet been updated. The owner backed up and uploaded that child `.htaccess` separately; HTTP `/api/v1/site-config` and direct `/api/index.php` then returned 403, while HTTPS versions retained JSON 200 and 404 respectively. This closes the tested public API transport gap. Existing `www.livinlively.ca` and `livinlively.com` aliases returned 302 to `https://livinlively.ca`; their HTTPS responses had a valid certificate and the same short host-only HSTS, with no `includeSubDomains`. Review alias certificate/renewal ownership before lengthening HSTS. The short trial is not long-term enforcement.

This checked page boot only; it did not authenticate a client, practitioner or administrator. The initial generic Playwright Chromium launch failed because that browser binary is not installed locally; rerunning with the installed Edge channel passed. Exact HTTP `portal.copihue.ca/admin/` and bare `/admin` both now return one 302 to the correct HTTPS Admin URL after their old Netfirms cache entries expired (`Age: 0` on recheck). The fresh query variants had already proved the origin rules before cache expiry.

Before a release decision, complete authenticated hosted sign-in/callback and API checks, then consider changing tested page redirects to 301 (or 308 only if every client/hosting path has been tested). Recheck all hosts and APIs, including direct HTTP access, before increasing HSTS duration. Confirm certificate renewal ownership before a long HSTS period. CSP, cache, no-sniff, referrer, cookie and provider/endpoint controls need their own per-host review; a redirect alone does not close SEC-03 or the real-data gate.

For rollback, restore the one backed-up root `.htaccess` at the same directory; retain all other files and the record of which requests failed. If a CDN/proxy caches an earlier 200 or 302, use a fresh path/query and confirm the server-side response before concluding rollback succeeded. Do not restore an older application package or database to undo a rewrite rule.
