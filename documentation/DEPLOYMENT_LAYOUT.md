## Uploads

Extract each archive's contents directly into its destination. Include hidden `.htaccess` files. Do not create another enclosing directory. The clinic portal package includes `index.html`, `assets/`, `api/`, and share-preview scripts. Upload it once to the common portal directory; both clinic hostnames serve those same files through Netfirms folder mappings. Use directory mappings, not redirects to a single clinic hostname. Each hostname retains its HTTPS certificate.

The general landing package belongs only in `/public_html/wellness-portal`; it includes the separate `admin/` build and its thin API entries. The Wellnexa marketing build is independent and is not generated by `scripts/build-deployment.ps1`. Its own public catalogue bridge is included in `Wellnexa/dist/api/`; do not replace it with the general PHP API entries.

The optional `wellness-api-public.zip` contains thin public API entries, not the backend. If deploying these separately, extract into `api/` beneath `/public_html/livinlively.ca`, `/public_html/wellness-common-portal`, or `/public_html/wellness-portal` as applicable. The portal and landing archives already include these entries. They resolve the single private `/wellness-api` directory at the existing relative depth. The mail bridge archive is a separate existing mail-host integration, not a clinic or marketing website package.

Preserve private `.env`, runtime data, uploaded files, and existing permissions. Follow the feature release guide for any database migration before deploying matching code; a directory-layout change alone requires no migration. Back up affected files first, retain old hashed assets through rollout, and refresh browsers afterward. A common portal update affects all clinics, so verify both after every release.

## Build and manifest

From a clean committed source revision:

```powershell
./scripts/build-portal-only-deployment.ps1 -ReleaseName YOUR-UNIQUE-PORTAL-RELEASE
```

This builds only the shared portal and records its source revision, checksum, destination and pending hosted acceptance. For a full API/frontend release, use `build-deployment.ps1` or the applicable feature wrapper. Full release manifests include destination mappings. The full builder defaults to the active Livin’ Lively public/portal URLs and accepts `-PublicUrl` and `-PortalUrl` HTTPS root overrides for another deployment; these override stale local frontend URL settings for that build and are restored afterward. The portal-only builder uses the active root portal URL so a stale local value cannot generate a retired destination. Receipt and distance-fee wrappers use the same `wellness-common-portal.zip` filename. Older portal ZIP names are superseded for newly generated releases; historical release ZIPs are unchanged.

## Configuration

Keep each clinic registered to its own hostname in `clinic_hosts` when `CLINIC_MANAGEMENT_ENABLED=true`. Verify actual clinic IDs before changing `CLINIC_HOST_MAP`; it remains a fallback for configured API hosts. Host routing, authentication and permissions continue to isolate clinic records even though files are shared. Do not delete clinic data when retiring an obsolete hostname.

The private API fallback settings for the original clinic are:

```dotenv
CLIENT_PORTAL_URL=https://livinlively.copihue.ca/client
VITE_PORTAL_URL=https://livinlively.copihue.ca/
CORS_ALLOWED_ORIGINS=https://livinlively.copihue.ca,https://wellnexa.copihue.ca
```

Add other exact origins only when an active browser application intentionally calls this API across origins. Origins have no path or trailing slash; do not use `*` with credentials. Portals call same-origin `/api/v1`. The Wellnexa catalogue bridge calls its fixed upstream on the server, so that bridge needs no browser CORS allowance.

For `Frontend` production builds, use `VITE_PUBLIC_URL=https://livinlively.ca/` and `VITE_PORTAL_URL=https://livinlively.copihue.ca/`. These are build-time public settings; changing the private API `.env` does not rebuild frontend bundles. Internal portal links and authentication callbacks derive their origin from the current clinic. `Wellnexa` has separate marketing build settings targeting `https://wellnexa.copihue.ca/`.

Remove retired hostname entries from hosted routing, CORS, and identity-provider redirect/logout registrations after checking that active callbacks remain registered. Local scripts and docs do not change hosted configuration. The old `/public_html/wellness` directory is retired and must not be recreated by deployments.

## Acceptance

1. Open both clinic `/availability` pages in fresh tabs. Check each clinic name, services, practitioners and location.
2. Select an available slot. **Book this time** must use that clinic's hostname and preserve service, practitioner, duration and time parameters.
3. Check client sign-in returns to that clinic's `/client/auth/callback`; verify staff sign-in and authorized clinic access separately.
4. Check both marketing sites, their booking links, and the general landing/admin page. Confirm same-origin APIs return JSON rather than SPA HTML.
5. When backend changes are included, complete the feature-specific hosted acceptance checks. Local builds and browser fixtures do not prove hosted database or identity-provider acceptance.

To roll back the shared frontend, restore its previous index, routing files and matching assets together. All clinic portals roll back together. Preserve the release manifest and backup.
