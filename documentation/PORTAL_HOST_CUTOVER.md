# Willow portal host cutover — October 2026

The Willow guest catalogue, client account, staff workspace, and same-origin `/api/v1` entry point move from `https://portal.copihue.ca/` to `https://willowwellness.copihue.ca/`. The old host becomes a neutral Copihue landing page with a Willow link. It does **not** offer generic sign-in or a clinic-membership list yet; those require the planned product identity/membership service. The generic landing package redirects old Willow `/client`, `/staff`, `/practitioner`, `/admin`, `/services`, `/practitioners`, `/availability`, and `/book` links to the new host, preserving their path and query string. It returns 404 for the old same-origin API and share-preview scripts. Existing tabs on the old host must be refreshed.

The release builder emits `wellness-portal.zip` for the **new Willow host**, `wellness-public.zip` for the existing public website, and `copihue-portal-landing.zip` for the **old neutral host**. The private API remains one application; these are thin public entry points, not separate databases. No SQL migration is required solely for the host change. If a release also contains feature migrations, follow that feature's migration instructions separately.

## Order of operations

1. Confirm that `willowwellness.copihue.ca` has valid HTTPS and identify its exact Netfirms document root. Do not assume it is the old `/public_html/wellness-portal` directory or upload there without checking. Back up the existing `portal.copihue.ca` document root before replacing it.
2. In the staff SPA app registration, add `https://willowwellness.copihue.ca/` as an exact redirect and logout destination. In the customer identity app, add `https://willowwellness.copihue.ca/client/auth/callback` and `https://willowwellness.copihue.ca/client` as the required SPA callback/logout destinations. Retain old callbacks during the cutover/rollback window. Do not place identity secrets in the frontend.
3. Upload the contents of `wellness-portal.zip` to the **new Willow document root** (not a nested folder). It includes the SPA, `/api` entry points, `.htaccess`, and share-preview scripts. The shared private API and `.env` remain in their existing private location. Deploy the matching private API archive if this release includes backend changes not already live.
4. In the **live private** `.env`, set `CLIENT_PORTAL_URL=https://willowwellness.copihue.ca/client`. Keep the exact existing CORS origins that are still needed and add the Willow origin if required for cross-origin calls; do not use `*`. Deployed Willow portal API calls are same-origin. Local `.env` values and package examples do not update Netfirms automatically.
5. Verify Willow's guest root, service booking deep link, practitioner share-preview, client Google/Microsoft sign-in and callback, staff sign-in, and same-origin API. Send a new test appointment and check its email/SMS links and `.ics` URL. Previously sent links should be tested through the old-host redirect.
6. Only after Willow works, upload the contents of `copihue-portal-landing.zip` to the old `portal.copihue.ca` document root. Confirm `/` is neutral and `/client` plus a service-booking link redirect to Willow. The generic host deliberately does not authenticate users or enumerate clinics yet.
7. Upload the matching `wellness-public.zip` to the existing Willow public website so its booking links point to the new portal. Test the public-site booking handoff and account-status link. Once rollback is no longer needed, remove obsolete callbacks and old Willow assets from the neutral document root through a reviewed cleanup, retaining the backup.

Do not redirect all requests from the old host: the root is now its own landing page. The generic page has no client or appointment API and does not claim a cross-clinic sign-in experience is live.
