# Multi Tenant Development Path

This plan records the agreed direction for offering the application to more than one independent clinic. It is a **future development track**, not a statement that the current deployment is tenant-safe. The current practitioner beta remains a single-clinic pilot. No second clinic should be onboarded until the isolation and onboarding gates below pass.

## Product and identity boundary

An application tenant is a clinic or other independently administered customer organization. It is not the same thing as a Microsoft Entra directory, a domain, a location, or an individual practitioner. One clinic may have several locations; one person may have authorized memberships in more than one clinic. Sharing an identity must never share clinic records or permissions implicitly.

Use a dedicated, standards-based identity provider for product sign-in, separate from the operator's Microsoft 365 workforce directory. The provider handles authentication, MFA, recovery and tokens; the application owns clinic invitations, memberships, roles and resource authorization. Do not build a new password, MFA and recovery system as part of this track. An approved customer-owned workforce login may be federated later, but is optional and must produce a trusted identity that the application explicitly links to a clinic membership. Microsoft Entra External ID is a candidate, not a committed provider or procurement decision.

The first clinic administrator is established by a controlled, audited operator onboarding process. Thereafter, an authorized clinic administrator manages staff invitations and deactivation **inside this application's portal**, within that clinic's delegated permissions. Customers do not receive administrator access to the shared identity directory. Email address, sign-in success, directory group, selected URL and browser-supplied clinic ID do not by themselves grant clinic access.

## Client access through clinic portals

The neutral `portal.copihue.ca` site may later offer an authenticated index containing only clinics and independent practices already linked to the verified identity. Its October 2026 landing page is public only: cross-clinic sign-in and membership listing have not been implemented. Willow's clinic portal moves to `willowwellness.copihue.ca`; see [Portal Host Cutover](PORTAL_HOST_CUTOVER.md). Following a clinic's direct link must continue to work without first visiting this hub.

A client may follow Clinic A's public booking link to Clinic A's branded portal, sign in with Google, and access only their Clinic A client record. Later, the same person may follow Clinic B's booking link to Clinic B's portal and use the same Google account. Clinic B resolves its own clinic context from trusted host configuration, then links that verified identity to a **separate Clinic B client record** through Clinic B's registration or verified claim process. The second sign-in does not import, reveal or merge Clinic A's profile, appointments, notes or consents. A general clinic switcher is not required for this portal-driven journey.

The identity-provider account is a sign-in identity, not a clinic's client-record ID. A clinic-local client ID may coincidentally match an ID in another clinic or differ from it; access always uses the clinic and client record together. Model a verified identity as capable of multiple distinct clinic-client links, while preventing duplicate or conflicting links within one clinic. The present `customer_client_links.identity_id` primary key permits only one client link globally and therefore needs an additive migration before this journey is enabled. Preserve existing approved links when changing that key.

An existing identity-provider session may make Clinic B sign-in seamless, but this is not guaranteed and does not transfer Clinic A's portal session or authorization. Clinic B must obtain or validate its own authentication result and application session, recheck the Clinic B client link, and safely handle an unlinked or inactive client. Do not share a broad domain-wide application cookie or place tokens in the booking handoff URL. Signing out of one portal and single sign-out across portals need an explicit, tested policy; neither should be inferred from a shared Google account.

## Application and deployment boundary

Keep one versioned core API and one authoritative scheduling implementation. The existing separately built public site and portal are a useful starting point: a customer may use their own public website and link to a hosted, clinic-branded booking/portal experience. Customer-owned frontends are a later, explicitly supported integration tier; they require documented API contracts, consented scopes, rate limits, stable public projections, versioning and operational support. A separate frontend does not require a separate API codebase or a separate backend service per clinic.

Resolve tenant context on the server from a validated identity and active membership, then check the requested resource's clinic and any narrower practitioner, location or client relationship. Hostname or path may help route and brand the experience, but it is not the authorization boundary. Background workers, caches, files, exports, reports, audit searches, notifications, provider credentials and support tooling must follow the same tenant scope. Platform-wide support access, if introduced, requires explicit just-in-time authority and audit rather than an ordinary clinic role.

The database-isolation model remains open: compare a shared database with enforced tenant keys against separate databases per clinic using security, restore/export, operations, migration and cost evidence. Existing `clinic_id` fields are a starting point, not proof of complete isolation. Confirm data residency, retention and clinic-specific sender/integration ownership before choosing the hosting model.

## Virtual clinic of independent practitioners — confirmed product direction

The product owner confirmed an Ontario-first virtual clinic that can onboard many independent practitioners. `independent_practitioners` is a clinic operating mode, **not** a way to bypass MT1–MT3 or an assertion about employment, legal custody or merchant status. The portal alone may provide the complete branded public website, practitioner directory, service catalogue, booking and later products; a separate website is optional and may deep-link to the same portal. The clinic can provide an administrator and optional shared assistance, but does not thereby own practitioner client records.

One verified person may use the same login with multiple independent practitioners. A clinic portal can show that person's authorized relationships and appointments, but each practitioner has a distinct client relationship and profile. The name, email, phone, address, preferences and clinical material that Practitioner A maintains must not be read or overwritten by Practitioner B merely because both reference the same identity. Identity-provider details may be suggested to a client starting a new relationship only after the client confirms them; another practitioner's overrides are not copied. A practitioner-created client without login remains private to that practice until a verified linking flow connects the identity. This requires new relationship/profile storage and a migration from today's single clinic-wide `users`/`client_profiles` representation; a UI-only filter is insufficient.

| Access path | Intended default | Explicit expansion |
| --- | --- | --- |
| Owning practitioner | Their own client profile, appointments and records | May initiate a scoped ongoing share, appointment coverage or reviewed transfer |
| Other practitioner | Public colleague profile and shared availability only | Sees only the permitted client/appointment fields within an active grant; no implicit client-list membership |
| Virtual-clinic admin or delegated reception | The minimum contact, booking and payment fields needed for assigned assistance | Additional operational duties require an auditable grant; clinical records are not included by a clinic-admin role |
| Client | Their own relationship-specific profiles and appointments in the portal | May establish a separate relationship with another published practitioner; controls the applicable sharing/consent choices |
| Platform operator | Tenant configuration and support metadata, not routine clinical access | Exceptional support access requires separate authority, purpose, time limit and audit |

Two sharing workflows are required. **Ongoing client sharing** grants a named practitioner a documented, revocable scope and purpose for a specified relationship and time period; sharing contact data does not automatically share clinical notes, files, consents or all history. **One-appointment coverage** grants a covering practitioner only the appointment, minimum contact/logistics and specifically authorized care context for that assignment and a limited follow-up window. The owner relationship remains with the original practitioner; store the owner/responsible practitioner separately from the actual performer and the grant. Coverage must recheck eligibility and scheduling, require acceptance, tell the client about the provider change, expire/revoke access, and preserve original authorship and audit history. Full relationship transfer is a third, separately reviewed operation. The legal consent/custodianship policy is to be approved for the operating agreements and profession; software must record the chosen basis rather than infer consent from a practitioner click. See the [Ontario IPC's Circle of Care guidance](https://www.ipc.on.ca/en/health-individuals/consent-and-your-personal-health-information) for the distinction between care-related sharing and general access.

Practitioners control their own published services/prices, availability, public profiles, practice policies and notification preferences, subject to explicit clinic publication and safety rules. Clinic-owned shared rooms, portal branding and optional reception remain separate resources. The existing unrestricted clinic-wide booking-client search/address lookup must be replaced or narrowly delegated for this mode; direct IDs, lists, counts, exports, reminders, dashboards and background workers require the same relationship checks. A practitioner may request an audited export of their own client details, appointments and permitted records, excluding material owned by or restricted to another practitioner. The export format, custody/retention obligations and departure process require a reviewed policy before release.

For money, a practitioner's choice between self-handled and clinic-assisted collection controls **who performs collection**, not automatically who legally sells, receives funds or issues a receipt. Model seller/merchant of record, payee, refund authority, settlement and invoice/receipt identity explicitly per practitioner and transaction. The clinic and individual practitioners may both publish products, each with an explicit seller and inventory/fulfilment owner. The first commerce increment should support separate seller-specific transactions; a mixed-seller cart or pooled checkout is deferred until the processor, agreements, tax/accounting treatment and reconciliation are settled. No raw card details enter the application. Appointment and product notifications carry the responsible practice/clinic branding and use scoped sender configuration; no practitioner gains another's recipient list.

Delivery gates for this mode:

1. Agree the virtual-clinic operating agreement, practitioner stewardship/custody matrix, delegated-admin fields, client sharing basis and seller/merchant choices. Complete MT0 and design additive migrations preserving Willow's records.
2. Complete MT1–MT2 and prove a synthetic second clinic is tenant-isolated, including identity links, workers, exports and operational support access.
3. Implement practitioner-specific client profiles and relationship authorization. Test two practitioners with the same client login but different names, contacts and private records; neither may enumerate or mutate the other's data through any endpoint.
4. Implement and audit ongoing sharing, one-appointment coverage, revocation, practitioner departure and scoped export. Test expired grants, direct-ID attacks, canceled/reassigned bookings, notifications and On-Site constraints.
5. Complete MT3 portal/clinic onboarding, then pilot with real Ontario practitioners in controlled cohorts. Do not impose a product cap on the number invited, but verify load, support, privacy and payment operations before broad invitations. Add clinic-assisted payments and seller-specific products in later gated increments.

Open implementation decisions are the exact administrator/reception field-level permissions, legal custodian/record-transfer policy, merchant-of-record and payout arrangements, processor capabilities, product tax/fulfilment rules, and whether a later mixed-seller cart is worthwhile. These must be resolved before their respective features handle real records or money; they do not prevent the identity and isolation foundation from being built.

## Delivery sequence and evidence

| Milestone | Work | Exit evidence |
| --- | --- | --- |
| MT0 — Architecture and inventory | Record identity-provider criteria, existing clinic/data mappings, shared-resource inventory, threat model and database/hosting options. Preserve the current clinic's identity links and release path. | Reviewed decisions and migration plan; every API, job, cache, file and integration owner identified. |
| MT1 — Identity and memberships | Prove staff and client sign-in with the selected provider or adapters; model immutable issuer/subject identity links, multiple clinic-specific client links and per-clinic staff memberships/roles; design bootstrap, invitations, recovery, MFA and optional customer SSO. | Wrong issuer/audience/subject rejected; an uninvited identity receives no clinic access; removal takes effect; the same Google login can separately establish access to two synthetic clinic client records without sharing their data or roles. |
| MT2 — Tenant-safe application | Enforce tenant scope across reads, writes, lists, counts, exports, workers and support operations; make branding, configuration and provider settings clinic-specific where required. | Automated cross-clinic denial and concurrency tests plus hosted tests using two synthetic clinics; backups, restore and deletion/export procedures demonstrated for the chosen data model. |
| MT3 — Clinic onboarding and frontend contracts | Add controlled clinic provisioning and delegated staff management; define hosted portal/booking handoff, trusted host-to-clinic configuration and versioned API contracts for optional customer websites. | A second synthetic clinic is onboarded without code forks or manual database edits; its public site opens its own portal, where the same test client can register or claim a separate record. Neither clinic can access the other's records, and each can invite/deactivate only its own staff. Customer-owned frontend use remains disabled until its contract/security acceptance passes. |

Complete MT0 before selecting a provider or changing production identity configuration. MT1 and MT2 must be accepted before any second real clinic. MT3 is required for repeatable customer onboarding. This track may proceed alongside the single-clinic roadmap but must not delay or silently expand the current practitioner beta.

## Open decisions

- Select the identity provider and sign-in methods after a proof of concept for staff MFA, client sign-in, invitations, recovery, and optional customer-owned SSO. Confirm pricing and data residency before procurement.
- Decide whether staff and clients share one identity provider with separate application contexts or use separate trusted adapters. In either case, client sign-in must never create staff access.
- Choose the database/hosting isolation model and document incident containment, per-clinic backup/restore and migration consequences.
- Define the customer-owned website/API integration tier, including branding/domain ownership, support obligations and permitted data projections.

The requirements in [Master Requirements](MASTER_REQUIREMENTS.md) and architecture in [System Design](SYSTEM_DESIGN.md) remain authoritative. This document details the multi-tenant path and its acceptance gates; it does not authorize deployment or a new identity subscription.
