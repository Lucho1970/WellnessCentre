# Esther: separate SQL identity migration

This is maintenance SQL for **existing user 2, clinic 1**, not a new invitation approval feature or an automatic migration. No PowerShell, SSH, public runner, app route or new database table is required on Netfirms. Files are in `api/maintenance/esther-identity/`; run their contents in phpMyAdmin, never upload them into a public document root. Do not run them as numbered schema migrations.

The latest portal still has external practitioner sign-in disabled. **Provider setup and a rebuilt portal come first.** These scripts do not enable Gmail login by themselves. Follow [Practitioner invitation configuration](PRACTITIONER_INVITATIONS.md): separate staff External ID API/SPA registrations, Google enabled in the staff user flow, exact `/staff/external` callback, staff scope/consent and provider MFA, matching frontend settings and private API settings. Existing workforce recovery administrator login must work before changing Esther's binding. Verify migration 033's invitation/claim tables already exist; if not, back up and apply that maintained migration once. No other new schema migration is introduced here.

## Obtain a verified claim

1. Back up the hosted database and rehearse on a separate copy. Confirm Esther is user 2, clinic 1, with exactly one active practitioner record, a practitioner-only role and an active imported workforce membership.
2. Verify private `.env` has `STAFF_MEMBERSHIP_PILOT_ENABLED=true` and `STAFF_MEMBERSHIP_PILOT_USER_IDS=2` (preserve any previously reviewed pilot selection). The recovery administrator must stay outside the pilot. This ensures Esther's old workforce identity cannot bypass the changed membership through legacy login. The SQL cannot inspect `.env`; its `@pilot_configuration_checked=1` is a manual acknowledgement, not an enforcement switch.
3. Enable and test the configured staff invitation flow. Create a normal invitation for Esther's Gmail address **without an existing user ID**. Do not use the normal Approve button: it creates a new practitioner account and is not this migration.
4. Esther opens the invitation in a separate browser session and signs in with her own Google account. She submits her claim and gives you its verification code through your usual contact method. Confirm it with Esther; an email match alone is not identity verification.
5. Obtain the invitation ID from the administrator list. It must have a pending claim, no acceptance/revocation and a future expiry. The app's dedicated staff authenticator has already verified the claim's token signature, issuer, audience, authorized party and scope before storing its issuer/subject. SQL uses that stored claim, not a manually decoded token or a Gmail lookup. The default invitation expires in 48 hours.

## Review and stage

Open [00-review.sql](../api/maintenance/esther-identity/00-review.sql), set `@invitation_id` and run the complete file. It only reads rows. Record membership ID, version, old identity ID and practitioner ID. Expect user 2, clinic 1, active membership and workforce identity, pending claim, no acceptance/revocation and zero target clinic memberships. The external identity may not exist yet, so `new_identity_id` may be NULL.

Fill the parameters in [01-stage-identity.sql](../api/maintenance/esther-identity/01-stage-identity.sql): invitation and recovery administrator IDs, Esther-confirmed uppercase verification code, the exact private `STAFF_EXTERNAL_TENANT_ID` and `ENTRA_TENANT_ID`, reviewed membership ID/version/old identity ID, `@pilot_configuration_checked=1`, and confirmation `STAGE USER 2 IDENTITY`. This inserts only the exact unbound external product identity, with no account, grant or membership change. Existing identities are never overwritten or reactivated. Run the review again and record the new identity ID. If an existing target identity is inactive or has a clinic membership (including revoked/pending), stop and investigate. A staged unbound identity is harmless to authorization and is retained if migration is abandoned.

Do not change the original workforce link, local email, user ID, practitioner ID, roles, permissions, client associations, public profile, services, appointments, forms or availability. The SQL does not write those records.

## Apply

Fill [02-apply.sql](../api/maintenance/esther-identity/02-apply.sql) with the same reviewed parameters, the new identity ID and confirmation `MIGRATE USER 2`. Run the **whole batch in one phpMyAdmin request**. Do not execute chunks across separate requests or manually COMMIT after an SQL error. On any SQL error stop; explicitly ROLLBACK on the same connection if still available. Connection termination rolls back an uncommitted InnoDB transaction.

The multi-table UPDATE rechecks membership version, exact legacy identity/tenant, exact claim identity and code, clinic, active practitioner-only account, active recovery administrator and inviter, invitation/location eligibility, and absence of a target clinic membership. It updates the existing membership's identity and increments its version, approves the claim and consumes the invitation together. It does not create another practitioner. Expected result is `changed_rows=3`, `audit_rows=1`, `transaction_result=COMMIT`. Any other result rolls back. SQL errors require stopping rather than proceeding. Save the receipt's membership ID, old/new identity IDs and resulting version for rollback. Both operations record administrator/entity IDs, not raw provider subjects or verification codes, in audit metadata.

Have Esther continue at `/staff/external` using her Google account. Verify her usual practitioner record and existing appointments/forms, the recovery administrator's workforce login, wrong-clinic denial and denial of Esther's old workforce login. An existing browser access token must still encounter the current membership check. Hosted sign-in acceptance is separate from the local SQL rehearsal.

## Rollback

Review the current membership and ensure it is still active and bound to the reviewed new identity. In [03-rollback.sql](../api/maintenance/esther-identity/03-rollback.sql), use the **current** membership version from the successful migration receipt, the original old identity ID, the same invitation/new identity IDs and verification code, and confirmation `ROLLBACK USER 2`. Run the whole batch. Expected result is one changed membership row, one audit row and COMMIT. Stale versions, inactive identities, revoked memberships, changed grants or identity conflicts refuse rollback.

Rollback restores the same membership to the original workforce identity and increments its version again. It preserves the accepted invitation/approved claim as history and does not delete or reactivate either identity. Verify Esther's workforce login and denial of her external binding afterward. Do not disable membership enforcement as a shortcut: that can restore unintended legacy access. Keep the workforce account and legacy link until the tested migration/rollback decision is complete.

## Limits and validation

No hosted data is read or changed by the agent. The owner runs reviewed SQL through their existing database administration access. The scripts require InnoDB transactions and prepared-statement support, but no routine creation privileges. MySQL documents [multi-table updates](https://dev.mysql.com/doc/refman/8.0/en/update.html) and permits COMMIT/ROLLBACK in [SQL prepared statements](https://dev.mysql.com/doc/refman/8.0/en/sql-prepared-statements.html). Exact hosted MySQL/phpMyAdmin behavior and simultaneous claim/approval changes still need acceptance; do not claim MariaDB rehearsal proves all hosted concurrency behavior.

The local integration test runs the exact files against a disposable database, using synthetic claims and records only. It covers placeholder refusal, staged identity idempotency, stale/wrong IDs and codes, configuration acknowledgement, inactive/revoked/elevated accounts, expired/revoked invitations, occupied target identities, apply/retry, old/new identity authorization, rollback/retry and preservation of practitioner-related records.

Validation on 7 October 2026: all 40 standalone migration SQL checks and the reused 34 recurring-booking checks passed on disposable MariaDB 11.4.8. The exact four SQL files were executed, including guarded failures, successful migration, resolver checks, preservation of local records, rollback and retry refusal. PHP syntax and Git whitespace checks passed. No frontend/API runtime source changed, so frontend builds/browser regressions were not repeated. No hosted data or Entra configuration was changed; hosted MySQL/phpMyAdmin, actual Google sign-in and concurrent claim acceptance remain pending.
